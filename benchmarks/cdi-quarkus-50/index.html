Правила, защищающие измерение

  • Эталон из source/compiler/dependency/build/runtime evidence. Ответы и индекс Quill не используются для построения эталона.
  • Выбор anchors до результатов: фиксированный seed, список кандидатов и причины пропусков. Никакой замены неудачного вопроса на выгодный.
  • Одинаковые естественные вопросы обеим arms; без указания tools, runner hints и автоматических repairs. RU/EN варианты и независимые holdout-перефразирования.
  • Свежие независимые сессии отдельно от связной задачи. Один MCP на сессию; готовность индекса проверяется до начала. Cache cold/warm учитывается отдельно.
  • Факты отдельно от формата. Статический кандидат не равен runtime-доказательству. Неизвестный usage не ноль.
  • Отчет: точность, полнота/лишние факты, ALL, uncached, output, стоимость и readiness/end-to-end time. 4× не оправдывает удаление провальных случаев.

Ожидаемые факты: prefix, property_paths, value_types, defaults, open_map_segments.

Независимый эталон: Compiler parse config mapping hierarchy/annotations и версионные naming rules; открытые map segments обозначать шаблонами, не выдумывать полный список.

CQ-038 · Приоритет источников

Вопрос: Какое значение {config_key} получится в контексте {config_context}? Покажи приоритет источников и не раскрывай секретные значения.

English: Resolve {config_key} for {config_context}, explaining source precedence without revealing secrets.

Предусловие: configuration_usage; параметры config_context, config_key.

Ожидаемые факты: effective_value_or_redacted, winning_source, overridden_sources, unknown_sources.

Независимый эталон: Зафиксировать sanitized config snapshot с source ordinals/profiles; использовать независимый Config probe в изоляции, не копировать ambient user secrets.

CQ-039 · Build-time против runtime

Вопрос: Можно ли изменить {config_key} без пересборки? Покажи доказательства build-time/runtime поведения для используемой версии.

English: Can {config_key} change without rebuilding? Establish build-time versus runtime behavior for the installed version.

Предусловие: configuration_usage; параметры config_key.

Ожидаемые факты: phase, extension_definition, requires_rebuild, version_evidence.

Независимый эталон: Проверить version-matched extension config definition/metadata и документацию; одинаковый префикс ключа не доказывает фазу.

CQ-040 · Переименование config key

Вопрос: Что надо изменить при переименовании {config_key} в {new_config_key}? Отдели код, конфигурацию, deployment descriptors и тесты.

English: Plan renaming {config_key} to {new_config_key}, separating code, configuration, deployment descriptors and tests.

Предусловие: configuration_usage; параметры config_key, new_config_key.

Ожидаемые факты: must_edit, verify_only, external_contracts, dynamic_key_limits.

Независимый эталон: Compiler/source references плюс properties/YAML/deployment/test fixtures и динамическое формирование key; внешний deployment не объявлять полностью известным.

Радиус рефакторинга — 5 сценариев

CQ-041 · Изменение сигнатуры метода

Вопрос: Каков прямой радиус изменения сигнатуры {method}? Отдели callers, overrides, интерфейсы, тесты и косвенные зависимости.

English: Determine the direct blast radius of changing {method}, separating callers, overrides, interfaces, tests and indirect dependencies.

Предусловие: method_with_callers; параметры method.

Ожидаемые факты: direct_callers, overrides, contracts, must_edit, verify_only.

Независимый эталон: Независимые compiler-resolved usages и override hierarchy; method identity со строгой сигнатурой, source reflection/string lookups отдельной категорией.

CQ-042 · Изменение qualifier

Вопрос: Если изменить qualifier у {qualified_bean} на {new_qualifier}, какие injection sites и producers придётся проверить или изменить?

English: Assess changing the qualifier of {qualified_bean} to {new_qualifier}, including affected injection points and producers.

Предусловие: qualified_bean; параметры new_qualifier, qualified_bean.

Ожидаемые факты: binding_sites, must_edit, verify_only, ambiguity_risks.

Независимый эталон: Сравнить resolution до/после на изолированном snapshot; учитывать qualifier values/defaults, programmatic literals и конкурирующие beans.

CQ-043 · Изменение интерфейса

Вопрос: Что затронет изменение контракта {interface}: реализации, injection sites, decorators/producers и прямые пользователи методов?

English: Assess a contract change to {interface}, covering implementations, injection points, decorators, producers and direct method users.

Предусловие: interface_with_implementations; параметры interface.

Ожидаемые факты: implementations, di_sites, producer_decorator_sites, method_users, boundary.

Независимый эталон: Compiler type/override/use graph плюс CDI assignability и producer return types; внешние API consumers явно за границей snapshot.

CQ-044 · Class bean в producer

Вопрос: Как заменить class bean {bean} producer-методом, не потеряв qualifiers, scope, lifecycle и совместимость потребителей?

English: Plan replacing the class bean {bean} with a producer while preserving qualifiers, scope, lifecycle and consumer compatibility.

Предусловие: class_bean; параметры bean.

Ожидаемые факты: preserved_contract, producer_dependencies, must_edit, lifecycle_risks, verification.

Независимый эталон: Независимый bean contract до/после, deployment resolution и lifecycle obligations; не считать producer и class annotations взаимозаменяемыми.

CQ-045 · Изменение scope

Вопрос: Что изменится, если перевести {bean} в {new_scope}? Проверь состояние, proxy, lifetime зависимостей и контекст вызова.

English: Assess changing {bean} to {new_scope}, including mutable state, proxies, dependency lifetimes and calling contexts.

Предусловие: class_bean; параметры bean, new_scope.

Ожидаемые факты: state_risks, proxy_constraints, lifetime_changes, affected_consumers.

Независимый эталон: Прочитать поля и scopes resolved dependencies, contexts/calls; runtime concurrency и destruction проверять targeted tests, не объявлять потокобезопасность по scope.

Тесты и изменение кода — 5 сценариев

CQ-046 · Какие тесты затронуты

Вопрос: Какие тесты следует запустить после изменения {change_target} и почему? Отдели прямое покрытие от эвристически релевантных тестов.

English: Select tests for a change to {change_target}, separating direct evidence from heuristic relevance and coverage gaps.

Предусловие: production_symbol; параметры change_target.

Ожидаемые факты: direct_tests, indirect_tests, heuristic_tests, coverage_gaps.

Независимый эталон: Compiler test references, route/use assertions и existing coverage если есть; отсутствие textual references не доказывает отсутствие интеграционного покрытия.

CQ-047 · Mocks и test profile

Вопрос: Как {test_class} подменяет CDI-зависимости и конфигурацию? Что отличается от production и что такой тест не проверяет?

English: Explain CDI and configuration substitutions in {test_class}, differences from production and resulting coverage limits.

Предусловие: cdi_test; параметры test_class.

Ожидаемые факты: test_profile, mock_sites, alternative_beans, config_overrides, limits.

Независимый эталон: Проверить test annotations/profile/mock setup и test lifecycle; сверить injection resolution в test context отдельно от production.

CQ-048 · Generated против handwritten

Вопрос: Откуда появился {generated_type}, какой handwritten input или extension им управляет и что надо менять вместо generated-файла?

English: Trace {generated_type} to its handwritten inputs or generating extension and identify the correct place to make a change.

Предусловие: generated_component; параметры generated_type.

Ожидаемые факты: generated_artifact, generator, source_inputs, edit_target.

Независимый эталон: Build generated-source/classes mapping, processor/extension inputs и source hashes; generated proxy не считать ручной точкой изменения.

CQ-049 · Минимальный проверяемый патч

Вопрос: Переименуй {rename_method} в {new_method_name}, обнови все необходимые места и добавь или адаптируй узкий тест. Сохрани поведение и покажи проверку.

English: Rename {rename_method} to {new_method_name}, update required references and add or adapt a focused test while preserving behavior.

Предусловие: safe_method_rename; параметры new_method_name, rename_method.

Ожидаемые факты: patch, updated_references, behavior_preserved, compile_result, test_result.

Независимый эталон: До опыта скрыто зафиксировать references и acceptance tests; на отдельном checkout применить patch, compile и запуск focused tests; проверить reflection/config/API contracts и отсутствие изменений gold.

CQ-050 · Связная пользовательская задача

Вопрос: Разбери одну пользовательскую операцию {flow_anchor}: точку входа, DI-выбор, настройки, радиус изменения и подходящие тесты. Работай по шагам в одной сессии.

English: Investigate the user operation {flow_anchor} in one continuous session: entry point, DI selection, configuration, change impact and tests.

Предусловие: connected_flow; параметры flow_anchor, profile.

Ожидаемые факты: step_facts, consistent_bindings, cross_step_consistency, change_plan.

Независимый эталон: Выбрать связный flow с независимыми evidence на каждый из шести шагов; все arms получают одинаковые вопросы/anchors, последующие prompts не содержат эталонных ответов.

  1. Найди точку входа операции {flow_anchor} и её непосредственный обработчик.
  2. Проследи выбор CDI-зависимости в этой операции при {profile}.
  3. Найди связанные настройки и их определения для этого профиля.
  4. Раздели прямые вызовы, DI-связи и условные runtime-переходы на этом пути.
  5. Составь минимальный план изменения контракта этой операции и прямой радиус проверки.
  6. Выбери узкие тесты для плана; отметь пробелы доказательств и не повторяй весь предыдущий разбор.

Как адаптировать к приложению

  1. Зафиксировать revision, source/resources/build/dependency hashes, Java/Kotlin, framework/CDI version, namespace и sanitized profile/config.
  2. Независимо от Quill собрать capability/anchor inventory. Для каждого CQ-ID сохранить applicable/N/A/blocked и доказательство.
  3. Для applicable задач выбрать symbol/site и границы scope, подготовить reviewed expected values, альтернативы и запрещенные overclaims.
  4. Заморозить bound-suite и отдельный скрытый oracle manifest. Модели передавать только rendered prompt и общий публичный контекст.
  5. До платных вызовов проверить изоляцию, readiness, реальные hook events и отсутствие oracle/helper leakage. Потом выполнять заранее зафиксированное расписание.

Существующие runners, ожидающие готовые expected facts, не должны получать этот template suite напрямую. Привязка Cryostat с независимыми эталонами подготовлена отдельно. Интеграция с платным runner и модельные прогоны не выполнены.
